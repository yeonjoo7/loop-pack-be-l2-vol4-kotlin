## 1. 문제 재해석

### 1.1 사용자 관점

| 사용자 유형 | 핵심 니즈 | 불편/리스크 |
|---|---|---|
| 일반 유저 | 원하는 상품을 빠르게 탐색하고 구매까지 이어지는 매끄러운 경험 | 느린 상품 조회, 결제 실패 시 재고가 차감된 채 복구 안 됨, 중복 좋아요로 인한 혼란 |
| 어드민 | 상품·브랜드 데이터를 안전하게 관리하고 주문 현황을 모니터링 | 잘못된 삭제로 인한 데이터 유실, 재고 수동 조정 오류 |

사용자가 실제로 겪는 문제를 구체적으로 기술하면 다음과 같다.

- 유저 A가 마음에 드는 상품을 발견하고 좋아요를 눌렀다. 네트워크 불안정으로 응답을 받지 못해 다시 눌렀다. 시스템이 중복 처리를 해버리면 유저는 혼란스럽다.
- 유저 B가 마지막 재고 1개를 담아 결제를 시도했다. 동시에 유저 C도 같은 상품을 주문했다. 둘 다 결제에 성공하면 재고는 -1이 된다.
- 어드민이 실수로 브랜드를 삭제했다. 해당 브랜드의 상품이 노출 중이었다면 유저들은 존재하지 않는 브랜드의 상품을 보게 된다.

### 1.2 비즈니스 관점

- 상품 탐색 → 관심 표현(좋아요) → 구매 전환의 퍼널을 시스템이 지원해야 한다.
- 재고가 부족한 상품은 주문되어서는 안 된다. 재고 정확성이 곧 신뢰도다.
- 브랜드 삭제 시 하위 상품도 함께 삭제되어야 데이터 일관성이 유지된다.
- 주문 시점의 상품 정보(가격, 이름)가 보존되어야 분쟁·정산 근거가 된다.
- 좋아요 수는 상품의 인기도를 나타내는 지표로, 정렬 기준으로 활용된다.

### 1.3 시스템 관점

- **좋아요의 멱등성**: 네트워크 재시도나 사용자 연타로 인해 좋아요가 중복 생성되거나 없는 좋아요를 삭제하려 할 때 오류 없이 처리해야 한다.
- **재고 동시성**: 여러 사용자가 동시에 동일 상품을 구매할 때 재고가 음수가 되어서는 안 된다.
- **결제 연동**: 외부 결제 시스템은 실패할 수 있다. 결제 실패 시 주문과 재고가 원래 상태로 복구되어야 한다.
- **Soft Delete 일관성**: 삭제된 브랜드·상품은 유저 API에서 노출되지 않으나, 기존 주문 스냅샷과의 참조 관계는 유지되어야 한다.

## 2. 액터 정의

### 2.1 일반 유저 (User)

- **인증**: HTTP 요청 헤더 `X-Loopers-LoginId` / `X-Loopers-LoginPw` 전달
- **권한**: 상품·브랜드 조회, 자신의 좋아요 관리, 자신의 주문 생성 및 조회
- **특이사항**: 좋아요·주문 API는 `userId`를 헤더에서 식별
- **접근 경로**: `/api/v1/` 하위

### 2.2 어드민 (Admin)

- **인증**: HTTP 요청 헤더 `X-Loopers-Ldap: loopers.admin` 전달
- **권한**: 브랜드·상품 CRUD, 전체 주문 조회
- **특이사항**: 일반 유저 API(`/api/v1/`)와 별도 경로(`/api-admin/v1/`) 사용
- **접근 경로**: `/api-admin/v1/` 하위

### 2.3 외부 결제 시스템 (External Payment System)

- **역할**: 주문 생성 시 결제 승인/거절 응답을 반환하는 외부 서비스
- **통신 방식**: 내부 서버에서 HTTP 호출 (동기 방식 가정)
- **실패 케이스**: 타임아웃, 결제 거절, 서버 오류 → 주문 롤백 및 재고 복구 필요

## 3. 도메인별 기능 명세

### 3.1 브랜드 (Brand)

#### 유저 기능

| 기능 | API | 설명 |
|---|---|---|
| 브랜드 단건 조회 | GET /api/v1/brands/{brandId} | 삭제된 브랜드는 404 반환 |

#### 어드민 기능

| 기능 | API | 설명 |
|---|---|---|
| 브랜드 목록 조회 | GET /api-admin/v1/brands | 전체 브랜드 목록 (삭제 포함 여부 정책 결정 필요) |
| 브랜드 생성 | POST /api-admin/v1/brands | name 중복 검증 |
| 브랜드 단건 조회 | GET /api-admin/v1/brands/{brandId} | |
| 브랜드 수정 | PUT /api-admin/v1/brands/{brandId} | name, description 수정 가능 |
| 브랜드 삭제 | DELETE /api-admin/v1/brands/{brandId} | Soft Delete, 하위 상품도 함께 Soft Delete |

#### 비즈니스 규칙

- 브랜드 삭제는 Soft Delete (`deleted_at` 기록). 물리 삭제는 없음.
- 브랜드 삭제 시 해당 브랜드의 상품도 Soft Delete 처리 (CASCADE Soft Delete).
- Soft Delete된 브랜드·상품은 유저 API에서 조회 불가.
- 브랜드 이름은 중복 불가 (생성 시 중복 검증 필요).

| 파라미터 | 값 | 기본값 |

- 재고(`stock_quantity`)는 0 이상이어야 하며, 주문 시 원자적으로 차감.
- 가격(`price`)은 양수여야 함.
- 상품 생성 시 연결된 브랜드가 존재해야 함 (삭제된 브랜드에 상품 생성 불가).

### 3.3 좋아요 (Like)

#### 유저 기능

| 기능 | API | 설명 |
|---|---|---|
| 좋아요 등록 | POST /api/v1/products/{productId}/likes | 멱등: 이미 존재하면 아무 일 없음 |
| 좋아요 취소 | DELETE /api/v1/products/{productId}/likes | 멱등: 없으면 아무 일 없음 |
| 내 좋아요 목록 | GET /api/v1/users/{userId}/likes | 유저가 좋아요한 상품 목록 |

#### 비즈니스 규칙

- 좋아요는 `(user_id, product_id)` 조합으로 유일 (DB UNIQUE 제약).
- POST 호출: 이미 좋아요가 존재하면 200 OK 반환 (에러 없음).
- DELETE 호출: 좋아요가 없어도 200 OK 반환 (에러 없음).
- 삭제된 상품에 대한 좋아요 등록 시도는 404 반환.
- 좋아요 수는 상품 목록의 `likes_desc` 정렬 기준이 됨.
- 좋아요 목록 조회 시 삭제된 상품도 포함할지 여부는 정책 결정 필요 (현재: 삭제된 상품은 목록에서 제외).

#### 멱등성 구현 방식 (설계 결정)

> **결정**: DB에서 `(user_id, product_id)`로 존재 여부를 먼저 SELECT한 뒤, 없으면 INSERT / 있으면 아무것도 안 함. 취소도 없으면 그냥 리턴.
>
> **대안 검토**: `INSERT IGNORE` 또는 `ON CONFLICT DO NOTHING` 방식도 가능하나, 애플리케이션 레벨에서 제어하면 로직 가독성이 높고 예외 처리가 명확해짐. 동시 요청에 대한 최후 방어선은 DB UNIQUE 제약이 담당.

### 3.4 주문 (Order)

#### 유저 기능

| 기능 | API | 설명 |
|---|---|---|
| 주문 생성 | POST /api/v1/orders | items: [{productId, quantity}] |
| 주문 목록 조회 | GET /api/v1/orders?startAt=&endAt= | 본인 주문만 조회 |
| 주문 단건 조회 | GET /api/v1/orders/{orderId} | 본인 주문만 조회 |

#### 어드민 기능

| 기능 | API | 설명 |
|---|---|---|
| 전체 주문 목록 조회 | GET /api-admin/v1/orders | 모든 유저의 주문 |
| 주문 단건 조회 | GET /api-admin/v1/orders/{orderId} | |

#### 주문 생성 처리 순서 (보장사항)

1. 요청한 각 상품의 재고 확인 (부족 시 즉시 오류 반환)
2. 각 상품의 재고 차감 (비관적 락 또는 조건부 UPDATE)
3. 주문 생성 (Order + OrderItem, 상품 스냅샷 저장)
4. 외부 결제 시스템에 결제 요청
5. 결제 성공 → 주문 상태 `PAID`로 갱신
6. 결제 실패 → 재고 복구, 주문 상태 `FAILED` 처리

#### 스냅샷 저장 필드

- `product_name`: 주문 시점의 상품명
- `price`: 주문 시점의 상품 단가
- `quantity`: 주문 수량

> 상품 정보가 이후 변경되더라도 주문 내역은 주문 당시 정보를 유지해야 한다. 이는 CS 분쟁 대응과 정산의 근거가 된다.

#### 주문 상태 전이

```
PENDING → PAID     (결제 성공)
PENDING → FAILED   (결제 실패)
PAID    → CANCELLED (취소, 이번 범위 외)
```

## 4. 애매한 요구사항과 설계 결정

### 4.1 좋아요 멱등성 구현 방식

**질문**: POST /likes를 두 번 호출하면 어떻게 해야 하는가? 에러를 내야 하나, 무시해야 하나?

**결정**: 멱등하게 처리 (두 번 호출해도 결과 동일, 에러 없음).

**근거**: 네트워크 재시도, 클라이언트 버그 등 현실적 상황에서 UX를 보호. REST의 멱등성 원칙에 부합.

**구현**: 애플리케이션 레벨에서 SELECT 후 분기. 동시성 문제는 DB UNIQUE 제약으로 보조. UNIQUE 위반 예외를 잡아 정상 응답(200)으로 변환.

---

### 4.2 재고 동시성 처리

**질문**: 동시에 여러 사용자가 마지막 재고를 구매하면 어떻게 처리하는가?

**결정**: 이번 범위에서는 미고려. 단순 재고 차감만 구현한다.

**근거**: 현재 단계에서는 기본 주문 흐름 구현에 집중. 동시성 이슈는 실제 트래픽이 발생하는 시점에 도입하는 것이 과도한 선행 설계를 피할 수 있다.

**추후 대응 방안**:
- 선택지 A: 비관적 락(`SELECT ... FOR UPDATE`) — 정확성 우선, 처리량 낮음
- 선택지 B: 낙관적 락(version 필드) — 처리량 우선, 충돌 시 재시도 필요

---

### 4.3 주문-결제 트랜잭션 경계

**질문**: 재고 차감과 결제 요청을 하나의 트랜잭션으로 묶어야 하는가?

**결정**: 재고차감 → 결제 → 성공 시 주문 확정, 실패 시 재고 복원 방식을 선택한다.

**처리 흐름**:
1. [TX1] 재고 차감 + 주문 생성(PENDING) → 커밋
2. 외부 결제 시스템 호출 (TX 밖)
3. 결제 성공 → [TX2] `order.confirm()` → PAID
4. 결제 실패 → [TX2] `order.fail()` → FAILED + 재고 복원
5. 결제 타임아웃 → 주문 PENDING 유지 (추후 배치로 처리)

**근거**: 외부 HTTP 호출을 트랜잭션 안에 포함하면 커넥션 점유 시간이 길어져 데드락·커넥션 고갈 위험.

**타임아웃 처리**: 결제 응답이 없으면 PENDING 상태를 유지한다. 재고는 차감된 상태로 남으며, 추후 PENDING 주문을 배치로 스캔하여 결제 상태를 확인하고 복원한다.

**1차 TX 커밋 후 서버 장애 시**: 주문이 PENDING으로 남는다. PENDING 주문을 주기적으로 스캔하는 배치를 통해 재시도 또는 복원 처리한다 (추후 구현).

---

### 4.4 브랜드 삭제 시 상품 처리

**질문**: 브랜드 삭제 시 하위 상품을 어떻게 처리할 것인가?

**결정**: CASCADE Soft Delete. 브랜드 `deleted_at` 설정과 함께 해당 브랜드의 모든 상품에도 `deleted_at` 설정.

**근거**: 물리 삭제 시 주문 스냅샷의 `product_id`가 orphan이 되는 문제 방지. 데이터 감사(audit) 목적으로도 유리.

**주의**: 상품에 연결된 좋아요는 삭제하지 않음. `deleted_at`이 있는 상품의 좋아요는 목록 조회에서 제외하는 방식으로 처리.

---

### 4.5 likeCount 갱신 방식

**질문**: 좋아요 등록/취소 시 Product의 likeCount를 어떻게 갱신하는가?

**결정**: `@TransactionalEventListener(phase = AFTER_COMMIT)` 방식으로 별도 TX에서 갱신한다.

**흐름**:
1. [TX1] Like 저장 → 커밋 후 `LikeCreatedEvent` 발행
2. [TX2] 이벤트 핸들러에서 `product.likeCount += 1`

**근거**:
- 같은 TX로 묶으면 Product 행에 잠금이 걸려 동시 좋아요 처리 시 병목 발생
- AFTER_COMMIT 방식은 Like TX 롤백 시 이벤트 자체가 발행되지 않아, "좋아요 없이 likeCount만 증가"하는 역방향 불일치를 차단
- likeCount 누락(Like는 저장됐지만 likeCount 미반영)은 허용 — like 테이블에서 언제든 재집계 가능

**likeCount를 Product에 두는 이유**: 상품 목록 조회 시 `likes_desc` 정렬을 위해 별도 JOIN 없이 바로 정렬 가능. 정확한 수는 like 테이블이 원본.

### 4.6 Brand ↔ Product 삭제 책임

**결정**: Brand는 Product를 모른다. 브랜드 삭제 시 Product Soft Delete는 Service 레이어에서 처리한다.

**흐름**: `BrandService.delete(brandId)` → Brand softDelete() + Product 일괄 softDelete()

**근거**: Brand 도메인이 Product 목록을 보유하면 두 집계 간 결합도가 높아진다. Service가 두 도메인을 조율하는 방식이 각 도메인의 독립성을 지킨다.

**대안**: `BrandDeletedEvent`를 발행하고 `ProductEventHandler`가 처리 — 결합도는 더 낮아지지만 이벤트 추적이 복잡해짐. 현재 범위에서는 Service 직접 처리로 단순하게 유지.

---

### 4.7 주문 시 쿠폰 적용

**질문**: 요구사항에 쿠폰이 언급되었으나 API 스펙에는 없음.

**결정**: 현재 범위에서 제외. 추후 `order_coupon` 테이블 추가 및 `discount_price` 필드 확장으로 대응 가능하도록 구조를 유연하게 설계.

---

### 4.6 어드민 브랜드 목록 조회 - 삭제된 데이터 포함 여부

**질문**: 어드민이 브랜드 목록을 조회할 때 Soft Delete된 브랜드도 포함해야 하는가?

**결정**: 어드민은 삭제된 브랜드도 조회 가능 (운영 목적). 유저 API는 삭제된 브랜드 제외.

## 5. 비기능 요구사항

### 5.1 성능

| 항목 | 요건 | 대응 방안 |
|---|---|---|
| 상품 목록 조회 | 페이지네이션으로 대량 데이터 제어 | page/size 파라미터, DB 인덱스 (brand_id, created_at, price) |
| 좋아요 순 정렬 | likes 집계 성능 부담 | like_count 비정규화 컬럼 (AFTER_COMMIT 이벤트로 동기화) |
| 주문 생성 | 재고 차감의 원자성 보장 | 재고 차감 + 주문 생성을 단일 트랜잭션으로 처리. 동시성 제어(락)는 이번 범위 미고려, 추후 도입 |
| 주문 목록 조회 | 기간 필터 + 페이지네이션 | created_at 인덱스 |

### 5.2 일관성

- 상품 스냅샷으로 주문-상품 데이터 분리 → 상품 변경이 기존 주문에 영향 없음.
- Soft Delete로 데이터 무결성 유지 (FK 참조 보존).
- 재고 차감과 주문 생성을 하나의 트랜잭션으로 묶어 원자성 보장.

### 5.3 확장성

- 유저/어드민 API 경로 분리로 권한 관리 명확화.
- 주문 상태 Enum으로 상태 전이 확장 용이 (취소, 환불, 교환 등 추후 추가 가능).
- 쿠폰, 배송지, 리뷰 등 도메인 확장 시 기존 테이블 구조 변경 최소화.

### 5.4 보안

- 인증은 헤더 기반 (`X-Loopers-LoginId`/`LoginPw`, `X-Loopers-Ldap`).
- 유저는 자신의 주문/좋아요만 접근 가능 (소유권 검증 필요).
- 어드민 API는 헤더 값 검증으로 접근 제한.
- 헤더 기반 인증은 프로덕션 수준의 보안이 아니므로, 추후 JWT/OAuth 전환 고려.

### 5.5 운영성

- Soft Delete로 실수 복구 가능.
- 주문 스냅샷으로 데이터 감사 추적 가능.
- 주문 상태 이력 관리로 장애 시 원인 파악 용이.
- 결제 실패 시 보상 트랜잭션 실패 케이스에 대한 운영 알림 체계 필요.
